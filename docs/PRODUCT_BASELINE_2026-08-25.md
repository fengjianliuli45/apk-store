# Stopwatch 产品与首发判定基线

> 日期：2026-08-25
> 状态：首发版本现行基线（FZ-01～FZ-06）
> 范围：本文件只收敛已确认的首发产品、阶段目标、数据采集、彩蛋和训练停止规则；后端、完整社交与其他并行问题由各自分支处理。

## 0. 首发冻结登记

### FZ-01 阶段训练目标与周期

- **状态**：已完成、已验收、首发冻结。
- **冻结日期**：2026-08-25。
- **权威实现**：`fitness-planner/` Python 引擎；`flutter/lib/planner/` 为 Flutter 端同步实现。
- **首发口径**：默认阶段周期 4 周；过程完成率至少 80%；至少 3 个有效训练周和 2 次可比较测量；满足数据质量、安全门槛及至少一项成果指标后判定 `achieved`；其中表现提升达到 2.5% 必须由两次可比较训练确认；未达标默认 `extended` 2 周。
- **解锁结果**：可靠达成第一阶段后，引擎输出 `pet_hatchling`；这里只冻结解锁条件和事件，不冻结后续宠物完整玩法或视觉表现。
- **模型边界**：垂直领域大模型可解释计划、陪伴和提出候选调整，但不得直接判定阶段达成、绕过安全规则或触发解锁。
- **验收证据**：Python 103 项测试通过；Flutter 13 项相关测试通过；相关 Dart 静态分析无问题；计划 JSON 版本为 `1.1`。

冻结后，其他首发文档和最终设计稿必须引用本节，不得重新定义阶段周期、达成条件、延期规则或模型权限。只有出现安全缺陷、实现不可行、法规要求或明确的产品负责人变更决策时才能解冻；解冻必须记录原因、影响范围、迁移方案、复测结果和新版本号。界面文案、进度呈现和动画可以继续定稿，但不得改变上述业务语义。

### FZ-02 低阻力数据采集与阶段认定

- **状态**：已确认、已验收、首发冻结。
- **冻结日期**：2026-08-26。
- **默认体验**：用户开始训练不需要先填写体重、腰围、照片或体脂率；训练过程自动采集动作、组数、次数、负荷、有效时长和完成情况。
- **身体数据**：体重、腰围、进度照片、体脂率及设备数据全部可选，允许跳过和稍后补录；缺失时不得阻止训练、生成计划或完成阶段。
- **训练后反馈**：首发只保留一个低成本快捷反馈，默认选项为“轻松 / 合适 / 吃力”；非必要问题不得阻塞训练总结。
- **达成路径**：用户可通过“执行与数据质量门槛 + 两次确认的训练表现提升”达成，也可通过“执行与数据质量门槛 + 可靠身体趋势”达成；身体数据不是训练表现路径的隐性必填项。
- **提示策略**：仅在复评或确实能提高判断质量时渐进式邀请补充数据；说明收益、允许立即跳过，拒绝后不进行高频提醒。
- **不足处理**：数据不足返回继续观察或 `extended`，不得显示“训练失败”，也不得为了宠物解锁推断或伪造身体变化。
- **隐私边界**：照片默认私密；健康平台、穿戴设备和群体参考数据必须单独授权，拒绝授权不降低基础训练能力。

其他首发文档和最终设计稿必须遵循“默认零额外操作”的方向。界面可以优化邀请时机与文案，但不得把任何身体测量改成首次使用、开始训练或宠物解锁的统一必填步骤。

### FZ-03 语音核心与宠物孵化彩蛋

- **状态**：已确认、首发设计冻结；动画与资产等待最终设计稿定型。
- **冻结日期**：2026-08-26。
- **统一载体**：语音助手 UI、孵化前的蛋和孵化后的宠物入口是同一个圆形载体，不新增并列的宠物悬浮入口。
- **孵化前身份**：圆形载体只表现为低干扰的“语音核心”，提供语音命令与动作预告；只使用系统提示音，不使用人格化声音，不提前说明其中存在宠物。
- **隐藏线索**：阶段推进时只允许短暂呼吸光、圆周波形或轻触觉等弱提示；不显示裂纹、宠物轮廓、倒计时、锁图标或解锁进度，不与开始训练主操作争夺注意力。
- **触发条件**：只有 `FZ-01` 可靠判定第一阶段为 `achieved` 并产生 `pet_hatchling` 事件后，才触发完整孵化彩蛋。
- **首次开口**：宠物孵化完成后才第一次使用人格化语音；这次开口是身份揭示的一部分。孵化前的系统提示音不得暗示宠物性格。
- **孵化后行为**：宠物收起时仍回到圆形语音入口；聆听、思考、说话使用同一位置的状态变化。专业模式保持克制，个性化模式允许更多表情与陪伴反馈。
- **可访问性**：孵化动画允许跳过且只自动播放一次；减少动态效果模式改用静态光线、字幕和轻触觉，跳过不影响宠物获得与后续使用。
- **首发范围**：隐藏线索、`pet_hatchling` 事件、孵化表现、基础外观/性格生成、首次字幕或语音、命名及“稍后处理”。AI 食物、Token、成长树、社交比较和完整陪伴系统留到后续版本。

最终设计稿可以继续确定材质、色彩、动画节奏、首句文案和宠物造型，但不得改变“同一圆形载体、孵化前系统提示音、阶段达成后才揭示身份”的产品语义。

### FZ-04 训练数据存储与跨设备同步架构

- **状态**：首发方案已确认、设计冻结；数据库迁移、Unity 协议与后端接口等待实施。
- **冻结日期**：2026-08-26。
- **单一权威**：Flutter 训练状态机负责计时、组次、暂停、停止和完成判定；Unity 负责教练呈现与结构化输入，不得自行判定训练或阶段完成。
- **本地优先**：训练开始、完成一组、修改实际次数/负荷、暂停、恢复、跳过、进入后台、停止和完成时自动写入本地 SQLite；Flutter 使用 Drift 管理表结构、事务和迁移。断网不得阻止训练。
- **数据分层**：首发至少包含 `workout_sessions`、`exercise_performances`、`set_performances` 和 `workout_events`；统计读取汇总表，关键事件用于异常恢复、审计和同步，不保存计时器每次刷新。
- **部分训练**：用户主动停止或 App/Unity 异常时保留已完成组、有效时长和停止状态；不得继续使用直接丢弃全部数据的 `abortWorkout()` 行为。
- **自动恢复**：重新打开 App 时若发现 `active` 或 `paused` 训练，提供“继续 / 结束”选择，不自动算作已完成，也不要求重复录入已保存组。
- **跨设备能力**：首发支持登录账号的备份与恢复；本地提交成功即向用户反馈，后台通过同步队列上传，网络恢复后自动重试。
- **活动训练约束**：同一账号同一时间只允许一台设备持有活动训练租约。另一台设备可查看已同步历史，但开始新训练前必须结束、接管或等待旧租约失效；接管必须保留旧设备已同步的部分记录。
- **同步标识**：业务记录使用全局唯一 ID，并记录 `created_at`、`updated_at`、`revision`、`device_id` 和同步状态；训练完成记录原则上追加而非覆盖，用户修正产生新修订，删除使用可同步的墓碑记录。
- **冲突规则**：组记录按全局 ID 去重；不同组可以合并；同一组出现并发修改时保留全部修订并以最新用户确认版本为当前值；服务端不得静默覆盖更完整的本地训练。
- **隐私边界**：默认不同步原始语音和摄像头视频；只同步训练所需结构化结果。身体数据、照片、设备数据和群体参考授权继续遵循 `FZ-02`。

当前 `SharedPreferences` 中的 `workout_log_v1` 仅作为旧数据源保留。实施时必须提供一次性、可重试且幂等的迁移：成功写入 SQLite 并校验后再标记迁移完成，不得先删除旧记录。

### FZ-05 训练暂停、停止与安全语音

- **状态**：首发交互已确认、设计冻结；状态机、持久化与 Unity 联调等待实施。
- **冻结日期**：2026-08-26。
- **暂停操作**：训练界面始终提供一键暂停；动作、计时、动作计数、休息倒计时、教练动画和语音预告立即冻结，不退出当前动作、不丢弃已有数据。
- **自动暂停**：App 进入后台、来电、Unity 异常或关键权限中断时先自动暂停；恢复必须由用户主动触发，并在重新开始动作前给出短倒计时。
- **结束操作**：按钮文案为“结束并保存”，始终可见但低强调；默认长按 1.2 秒完成，松开取消。无障碍模式提供“点击后再次确认”的等价操作，不强制长按。
- **保存规则**：停止后状态记为 `stopped`，保存已完成组、实际次数、负荷、有效训练时间和可选停止原因；当前未完成组记为 `incomplete`，不得像现有 `abortWorkout()` 一样丢弃全部现场。
- **阶段计算**：暂停时间不计入有效训练时间，正常组间休息单独记录；已完成组可进入负荷与安全复盘，`stopped` 场次不计为完整训练完成率，也不得触发羞辱、惩罚或宠物负反馈。
- **语音优先级**：“暂停 / 停一下 / 等一下 / 停下来”等本地安全关键词立即暂停且无需确认；“继续”在安全允许时经短倒计时恢复；“结束训练”先暂停再询问是否结束并保存。
- **紧急表达**：“受伤、胸痛、呼吸困难、救命”等表达立即暂停并显示紧急帮助入口，关闭普通陪伴对话；不得交给大模型自由生成诊断或处置结论。
- **识别不确定性**：低置信度的暂停命令宁可先暂停；继续、结束和其他有状态影响的命令必须确认。安全关键词首发必须本地可用，不依赖网络或大模型。
- **停止后体验**：首先显示已保存的组数与有效时长，提供“返回首页 / 稍后继续”；停止原因使用可跳过的快捷选项，不得阻塞保存或返回。

实施时用 `stopWorkout(reason?)` 取代直接清空状态的 `abortWorkout()`，并按照 `FZ-04` 在清理内存状态前完成数据库事务，再通知 Unity 停止呈现。

## 1. 已确认的产品基调

- 视觉以当前 `flutter/` 项目为准：冷白/浅青灰/暖灰渐变、黑色信息、电光青柠 `#BAFF00` 主操作、低干扰辅助入口。
- 正式客户端为 Flutter + Unity，覆盖 Android 与 iOS。
- Unity 首发支持男性/女性专业健身教练切换；当前先制作男性教练，女性角色、声音与动作资产必须在首发验收前补齐。专业教练与后续个性化宠物分开。
- 社区等功能不要求训练后解锁，但不能与训练首页的主操作争夺注意力。
- 首发不做装备推荐、商城、支付或物流。
- 首发保留有限语音命令和宠物彩蛋；完整宠物、AI 食物、模型合作与个性化语音属于后续迭代。

## 2. 规划引擎可用性结论

仓库包含两套同逻辑实现：

- `fitness-planner/`：Python 权威源。
- `flutter/lib/planner/`：App 离线运行的 Dart 移植，只通过 `PlannerGateway` 对 UI 暴露计划。

当前引擎已具备：

- 用户资料校验、TDEE 与营养目标。
- 周训练分肢、动作编排、课时预算和周容量。
- 初/中/高阶渐进规则。
- 默认每 4 周复评与减载，12 周建议切换方案或重审目标。
- 体重变化、连续无法完成、中断和目标变化触发器。

原有缺口：引擎只能生成训练周期，不能生成并判定“第一阶段目标”。本轮补充的公共模型如下：

```text
StageGoal
  id
  goal_type                 // strength / hypertrophy / fat_loss / recomposition / fitness
  start_at / planned_end_at
  cycle_weeks               // 默认取 progression.next_check_week，目前为 4
  baseline_metrics[]
  target_metrics[]
  adherence_target
  minimum_data_requirements
  status                    // active / due / achieved / extended / replaced
  confidence

StageAssessment
  stage_goal_id
  measured_at
  adherence_result
  performance_result
  body_trend_result
  data_quality_result
  achieved
  reasons[]
  next_action
```

实现状态（2026-08-25）：上述能力已在 Python 权威源与 Dart 离线移植中实现。Python 全套 103 项测试通过；Flutter 的阶段目标、计划同步和复评 13 项定向测试通过，新增 Dart 文件静态分析无问题。

垂直领域大模型的边界：模型负责对话、解释、语音陪伴、从非结构化反馈提取候选信息及提出调整建议；阶段达成、训练安全限制和最终计划版本仍由确定性规则与用户确认控制。模型输出必须记录模型版本、提示版本、输入摘要和采用/拒绝结果，便于将来训练与评估自有模型。

第一阶段默认使用引擎已有的 4 周复评周期。若数据不足或目标未达成，延长 2 周或生成下一周期，不因日期到达自动判定完成。

## 3. 阶段目标的可靠认定

这是产品内训练阶段判定，不是医学诊断或临床疗效认证。认定采用四层证据，禁止只凭单次体重、估算热量或累计打开时长。

### 3.1 数据质量门槛

- 身体测量尽量在相近时段和条件下完成；体重使用多日趋势而非单点。
- 强度/力量复测必须使用同动作、同动作标准、相同或可换算负荷。
- 数据不足时返回 `extended`，不得为了触发宠物彩蛋伪造达成。
- 用户疼痛、伤病、药物或健康状况明显变化时，暂停自动结论并提示寻求专业意见。

### 3.2 过程门槛

建议首版默认：

- 完成不少于计划训练场次的 80%；
- 至少覆盖 3 个有效训练周；
- 至少有 2 次可比较的基线/阶段末测量；
- 用户主动停止的训练保存已完成内容，但不把未完成场次记为完整完成。

80% 是产品初始参数，不宣称为医学阈值；应通过真实留存和达成率调整。

### 3.3 目标证据

| 目标 | 首选认定 | 辅助证据 | 不应单独使用 |
|---|---|---|---|
| 力量 | 标准化动作在同负荷下完成更多规范次数，或同动作安全负荷提高；进阶用户可选 1RM/估算 1RM 复测 | 训练容量、RPE/RIR 趋势 | App 自动计数、单次状态特别好的成绩 |
| 增肌 | 训练容量和力量趋势达到引擎目标，并有至少一种重复身体测量支持 | 围度、体重趋势、可选体成分 | 单次家用 BIA 数值、照片判断 |
| 减脂 | 多日体重趋势或标准化腰围达到个体阶段目标 | 计划完成度、饮食记录完整度 | 单日体重、估算运动热量 |
| 重组 | 腰围/体重趋势与力量或容量改善组合判定 | 可选体成分趋势 | 只看体重不变 |
| 体能/习惯 | 标准化任务表现改善并达到计划完成门槛 | 心率恢复、主观体感、持续性 | 只累计 App 打开时间 |

阶段达成建议使用：过程门槛全部通过，并达到该目标至少一个核心结果指标。身体结果受噪声影响时，可由能力提升和高质量训练完成共同达成，但必须向用户解释判定依据。

表现提升百分比按 `(当前标准化表现 - 基线表现) / 基线表现 × 100%` 计算。达到 2.5% 不能凭单次训练直接认定，必须在相同动作、相近负荷/动作标准与努力程度下，由两次可比较训练确认；否则只作为趋势提示。用户界面优先展示具体进步（例如“同重量多完成 2 次”），研究型百分比保留在引擎内部。

### 3.4 外部依据

- WHO 成人活动指南：成人每周应进行 150–300 分钟中等强度有氧活动或等量高强度活动，并至少 2 天进行主要肌群强化；适合作为长期健康基线，不直接作为个人阶段达成证明。https://www.who.int/publications/i/item/9789240015128
- ACSM 阻力训练渐进立场：训练应按经验、目标、强度、组次、频率与恢复逐步调整。https://acsm.org/education-resources/pronouncements-scientific-communications/position-stands/
- 1RM 系统综述显示其通常具有良好至优秀的重测信度，但首发面向新手时不强制极限测试。https://pubmed.ncbi.nlm.nih.gov/32681399/
- CDC 建议减重目标采用渐进、稳定方式，约每周 1–2 磅；具体目标仍须个体化，不应强迫用户追求上限速度。https://www.cdc.gov/healthy-weight-growth/losing-weight/index.html
- 美国体力活动指南支持逐步增加肌肉强化活动的频率和强度。https://odphp.health.gov/our-work/nutrition-physical-activity/physical-activity-guidelines/current-guidelines

## 4. 宠物彩蛋

首发不把宠物做成普通功能入口。使用低干扰彩蛋：

- 默认不显示进度条、不在首页解释养成系统。
- 在少数节点埋入模糊信号：首次生成阶段目标、首次完成整周、阶段复评前。
- 文案只提示“你的训练正在形成某种伙伴特征”，不展示物种和答案。
- 第一阶段被可靠判定为 `achieved` 后才播放完整诞生彩蛋。
- 宠物根据该阶段的训练响应、完成方式、恢复与行为特征生成，不由用户直接挑选。
- 彩蛋可跳过，之后可从“我的”重新观看。

## 5. 首发必须采集的数据

当前 `WorkoutLogEntry` 只有整场时长、完成组数和估算热量，不足以生成阶段目标、训练响应和后续宠物。应改为事件 + 汇总双层结构，优先使用 SQLite/Drift，不能长期只存 `SharedPreferences`。

本节的“必须采集”仅指训练运行时能够自动产生的数据。体重、腰围、照片、体脂率及外部设备数据遵循 `FZ-02`，均不是用户开始训练或完成阶段的统一必填项。

### 5.1 计划快照

- `plan_id`、`planner_version`、生成输入快照。
- 阶段目标、周期、计划训练日、动作、组次、负荷/自重、目标 RPE/RIR、休息时间。
- 调整原因和旧版本引用；计划更新不覆盖历史。

### 5.2 训练事件

Flutter 与 Unity 统一使用带 `event_id`、`session_id`、UTC 时间和版本号的 JSON 事件：

```text
session_started
exercise_started
set_started
set_completed          // 实际次数、负荷、RPE/RIR、用时
rest_started
rest_extended
rest_skipped
session_paused
session_resumed
session_stopped        // reason、已完成内容、是否保存
session_completed
```

Unity 负责渲染和动作状态；Flutter 训练状态机与本地数据库是业务事实源。事件先写本地 Outbox，联网后再同步，服务端按 `event_id` 去重。

### 5.3 身体与恢复

- 体重、腰围、可选体脂及测量条件。
- 睡眠、疲劳、酸痛、恢复自评。
- 可选设备数据必须记录来源与置信度。
- 原始敏感数据与匿名群体特征分开存储；加入群体参考必须单独授权。

## 6. 训练停止按钮

训练中必须同时存在两个不同目的的控制：

1. `暂停`：一键立即生效，冻结动作、计时和休息倒计时；用于短暂突发情况。
2. `结束并保存`：始终可见但低强调，长按 1.2 秒完成，松开取消；不得藏进更多菜单。无障碍模式允许二次点击确认。

结束后的行为：

- 立即停止 Unity 动画、计时、语音和传感器采集。
- 保存已完成的组、有效时长和停止原因，状态记为 `stopped`，不能像当前 `abortWorkout()` 一样直接丢弃全部记录。
- 进入“本次训练已停止”简版总结，提供返回首页和稍后继续（若计划允许）。
- 未完成场次不计入完整训练完成率，但已完成组可用于训练负荷和安全复盘。
- App 进入后台、来电、Unity 崩溃时先自动暂停；恢复后由用户选择继续或结束。
- 语音“停下”等不明确表达一律优先暂停；结束训练需要再次确认。

当前 Flutter 占位流程已有暂停、`abortWorkout()` 和结束按钮，说明状态机基础存在；真正接入前需要把 `abortWorkout()` 改为可保存部分训练的 `stopWorkout(reason)`，并把同一协议接入 Unity。
